# 구성품 규칙 점검

이 문서는 점검 당시 근거와 이후 수정 기록입니다. v0.0.0의 필수 대기 작업 목록이 아닙니다.

2026-11-12 기준으로 AGENTS.md·승인 계약·구성품 선언·현재 소스를 정적으로 대조했습니다. 기존 project/ 앱은 읽거나 변경하지 않았고 생성·설치·타입·기능·GUI 검사는 실행하지 않았습니다. 아래 동작 문제는 소스 흐름에서 확인한 불일치이며 실제 재현 결과는 아닙니다.

## 발견 이력과 수정 상태

### P1 — Electron 초기화 도중 종료 요청 전달 수정·동작 미검증

근거: [Electron index.ts](../../components/01-base/electron-backend/files/src/backend/index.ts)의 11~16행과 26~29행. close는 startup을 기다린 뒤에야 di.dispose를 호출하지만 startup은 별도로 di.lifecycle.initialize를 기다립니다. 초기화 중 SIGINT·SIGTERM·종료 요청이 와도 lifecycle에는 종료가 전달되지 않습니다. 대기 중인 initialize가 끝나면 의존 Service의 다음 initialize도 실행될 수 있고, 끝나지 않으면 종료도 계속 대기합니다.

이는 AGENTS.md의 “초기화 실패 시 후속 실행 차단”과 “초기화 도중 종료도 안전하게 처리” 기준 중 종료 조정 부분에 맞지 않습니다. 창 생성 후 di.start에서 처리되는 종료와 첫 lifecycle.initialize 중 종료를 구분해야 합니다. 후속 수정에서 첫 초기화 구간을 표시하고 close가 startup을 기다리기 전에 lifecycle.dispose를 호출하도록 변경했습니다. dispose의 즉시 종료 표시는 후속 초기화를 차단하며 실제 정리는 진행 중 초기화를 기다립니다. 동작 검증은 미실행입니다.

후속 수정·검사: DI가 존재하는 시점의 종료 요청은 lifecycle/runtime에 즉시 전달하고 startup과 정리가 서로 기다리는 순환을 피해야 합니다. 작은 대역으로 첫 initialize를 보류한 뒤 종료 → 첫 작업 완료 → 두 번째 initialize 미호출·정리 1회·새 창/통신 미시작을 확인합니다. 실제 Electron 종료는 별도 터미널에서 확인합니다.

### P2 — TCP 연결 종료 후 업무 추적 수정·동작 미검증

근거: [tcp.communication.ts](../../components/03-features/tcp/files/src/backend/communications/tcp/tcp.communication.ts)의 108~118행, 164~180행, 184~200행. Bridge 작업은 연결 종료/30초 제한과 Promise.race하지만 원래 작업 Promise를 별도 보관하지 않습니다. 연결이 닫히면 connection.done이 끝나고 연결 목록에서도 제거되므로 stop이 기다리는 목록에서 실제 진행 중인 업무가 빠질 수 있습니다.

따라서 접속을 끊은 client의 업무가 계속 실행되는 동안 stop이 완료되고 공유 Service가 해제될 수 있습니다. 연결 수 64개 제한도 이미 단절됐지만 실행 중인 업무 수를 제한하지 못합니다. 이는 “진행 요청 정리 → 업무 자원 역순 해제” 규칙과 어긋날 수 있습니다. 소켓 종료가 업무의 강제 취소를 뜻하지 않는다는 승인된 제한 자체를 문제로 본 것은 아닙니다. 후속 수정에서 실제 업무 Promise를 별도 집합으로 추적하고 기존 5초 종료 대기에 포함했습니다. 연결 종료 이후 늦은 응답은 계속 억제합니다. 회귀 테스트와 사용자 검증 절차를 추가했으며 실행은 하지 않았습니다.

후속 수정·검사: 연결과 독립적인 업무 Promise 집합을 실제 완료까지 추적하고 stop의 5초 대기에 포함해야 합니다. 보류 Bridge 실행 후 client 종료 → stop이 아직 대기하는지 → 작업 완료 시 정상 정리, 5초 초과 시 명시 실패와 늦은 결과 미전송을 사용자 검증 절차에 추가합니다. 진행 업무의 전체 수 제한을 새로 공개 계약으로 추가한다면 적용 전 별도 확인합니다.

## 이번에 정리한 불일치

- Composer 계약은 docs/contracts/, 공통 검증은 docs/validation/, 새 앱의 기능별 검증 원본은 각 files/docs/validation/으로 옮기고 문서 참조를 갱신했습니다. 타입 계약 코드는 소유 기능에 유지했습니다.
- AGENTS의 UDP·MQTT·Socket.IO 미구현 문구, 웹·Electron 계약의 과거 자동 검사 방침, 조립 계약의 react-common 누락 설명을 현재 승인 범위와 맞췄습니다. README의 “외부 연결 없음”은 외부 브로커 미접속과 loopback 검사 포함을 구분했습니다. rework-plan의 제거된 project-agents 참조와 과거 수동 Git 초기화 설명도 수정했습니다.
- 소스·검사 코드의 미사용 매개변수 _resolve·_request·_deps 등은 기존 camelCase 규칙에 맞춰 접두 밑줄만 제거했습니다. 공개 API·인수 순서·동작은 유지했습니다.
- 통신 선택 안내는 선택된 구성의 허용·필수·None만 공통 선택표에서 표시하도록 앞선 변경을 보존했습니다.

## 확인 범위와 미검증

표준 6개 구성의 기본·전체 허용 선택 총 12개 계획을 메모리에서 읽기 전용으로 조립해 선언 충돌·의존성·선택 영역 폴더·미선택 영역 제외와 생성 문서 링크를 확인했습니다. 앱 파일 출력·Git 초기화·설치·실행은 하지 않았습니다. 이 점검 시점의 업무 Bridge 자동 추가·Service/util 선택·사후 추가는 미구현 범위였습니다. 이후 선택 logger는 별도의 승인 계약에 따라 추가했으며 Electron 종료 전달은 이후 수정했으나 동작 미검증이며 TCP 업무 추적도 이후 수정했으나 동작은 미검증입니다.

변경 소스 10개의 문법·JSON 파싱·문서 링크 대상 59개·이름·추적 제외 대상·diff 확인이 통과했습니다. 링크가 끊긴 문서와 추적 중인 제외 대상은 발견하지 않았습니다. 이 정적 점검은 전체 타입 정확성·실제 통신/GUI·다른 OS·전체 조합 실행의 성공을 보장하지 않습니다. Phaser 준비 이벤트가 발생하지 않는 경우의 정리 무기한 대기와 Phaser 4.2.1 skipLibCheck는 이미 승인·문서화된 제한으로 남깁니다.
